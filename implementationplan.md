## Phase 2 — Cleaning & Pre-filtering

### Objective
Normalise all raw data into a unified schema, remove duplicates, detect language, and apply keyword pre-filtering to shrink the dataset before LLM extraction.

### Tasks

| # | Task | Detail | Output |
|---|---|---|---|
| 2.1 | **Build normaliser** | Map each source's raw format to the unified schema: `{id, source, url, date, rating, platform, app_version, language, text, thread_context}` | `processing/normalise.py` → `data/processed/normalised.jsonl` |
| 2.2 | **Language detection** | Use `langdetect` or `fasttext-langdetect`; keep English only (add Hindi/Hinglish fallback flag) | `processing/language_detect.py` |
| 2.3 | **Exact dedup** | SHA-256 hash on whitespace-normalised, lowercased text; remove exact matches | `processing/dedup.py` |
| 2.4 | **Near-duplicate removal** | MinHash with Jaccard threshold ≥ 0.85; keep the newest item from each near-dup group | `processing/dedup.py` |
| 2.5 | **Keyword pre-filter** | High-recall regex/keyword pass using seed phrases (expanded); keep items matching ≥ 1 phrase | `processing/prefilter.py` → `data/processed/prefiltered.jsonl` |
| 2.6 | **Funnel report** | Log and display: raw → language-filtered → deduped → near-deduped → pre-filtered | Console + `RUNLOG.md` |

### Data Funnel Example

```
Raw:              25,400
Language filter:  22,100  (−13%)
Exact dedup:      20,800  (−6%)
Near-duplicate:   19,500  (−6%)
Keyword prefilter: 6,200  (−68%)  ← sent to LLM
```

### Acceptance Criteria
- [ ] Every record in `normalised.jsonl` conforms to the unified schema.
- [ ] Zero exact duplicates remain.
- [ ] Near-duplicate pairs with Jaccard ≥ 0.85 are collapsed.
- [ ] Pre-filtered set is a manageable size for LLM calls (roughly 5,000–8,000 items).
- [ ] Funnel numbers logged to `RUNLOG.md`.

## Phase 3 — LLM Extraction & Verification

### Objective
Run each pre-filtered item through an LLM to classify relevance and extract the full structured taxonomy, then verify every extraction with deterministic code.

### Tasks

| # | Task | Detail | Output |
|---|---|---|---|
| 3.1 | **Define JSON schema** | Formal JSON Schema for the extraction output (all 18+ fields from the taxonomy); used to constrain LLM output | `extraction/schema.py` |
| 3.2 | **Build LLM client** | Provider-agnostic wrapper; reads model name from env; supports Gemini and Groq; exponential backoff; failover on 429 | `extraction/llm_client.py` |
| 3.3 | **Build batch extractor** | Batch 10–20 items per LLM call; JSON-schema-constrained output; cache result by `hash(text + prompt_version)` | `extraction/batch_extract.py` |
| 3.4 | **Build verifier** | Code-only (no LLM) checks: (a) `evidence_quote` is exact substring of original text (whitespace/case normalised), (b) all enum values are valid, (c) `example_queries` are exact substrings. Retry once on failure, then drop. Log drop rate. | `extraction/verify.py` |
| 3.5 | **Run extraction** | Process all pre-filtered items; checkpoint every batch; log progress | `data/extracted/extracted.jsonl` |
| 3.6 | **Separate by relevance** | Split into `core.jsonl` (relevance = core), `adjacent.jsonl`, `rejected.jsonl` | `data/extracted/core.jsonl` etc. |
| 3.7 | **Corpus size gate** | Count core items; apply gate logic | Console report |

### Extraction Prompt Template (Simplified)

```
You are a data-labelling assistant. For each user review about Google Photos,
determine if it describes difficulty FINDING or RE-FINDING an existing photo/video.

Classify as:
- "core": directly about searching, browsing, or re-locating photos that exist
- "adjacent": photos missing/deleted/not backed up (data issue, not search issue)
- "not_relevant": unrelated to retrieval

For "core" items, extract the following fields: [full taxonomy]

Output MUST conform to this JSON schema: [schema]

IMPORTANT: evidence_quote must be an exact substring of the original text.
```

### Gate Logic

```python
core_count = count_items("data/extracted/core.jsonl")

if core_count >= 3200:
    print("✅ Gate passed. Proceeding to Phase 4.")
elif core_count >= 1000:
    print("⚠️  Core count is {core_count}. Options:")
    print("  1. Extend date window beyond 24 months")
    print("  2. Add Hindi/Hinglish items")
    print("  3. Include 'adjacent' items with clear labelling")
    print("  STOP — awaiting decision.")
else:
    print("❌ Core count below 1,000. Investigate source failures.")
    sys.exit(1)
```

### Acceptance Criteria
- [ ] Every extracted item passes code-based verification.
- [ ] Drop rate is logged (expected < 10%).
- [ ] Core corpus has ≥ 3,200 items (or gate escalation triggered).
- [ ] `RUNLOG.md` updated with extraction stats and drop rate.

## Phase 4 — Aggregation, Clustering & Opportunity Scoring

### Objective
Compute all analytics, discover bottom-up themes, score opportunities, and generate audit/validation materials.

### Tasks

| # | Task | Detail | Output |
|---|---|---|---|
| 4.1 | **Compute aggregates** | Funnel, per-source/month counts, failure_stage distribution, failure × photo_type, clues remembered vs forgotten, clue × failure heatmap, outcomes, workarounds, example queries, regression/AI mentions | `analysis/aggregates.py` → `data/aggregates/*.json` |
| 4.2 | **Generate embeddings** | Embed `core_problem` sentences using a sentence-transformer (384–768 dims) | `index_builder/embeddings.py` → `data/index/embeddings.npy` |
| 4.3 | **Cluster** | HDBSCAN (preferred) or KMeans with k chosen by silhouette; filter clusters with ≥ 15 members; remainder → "Emerging Themes" | `analysis/clustering.py` → `data/clusters/clusters.json` |
| 4.4 | **Name clusters** | LLM pass: for each cluster, generate title, one-line definition, 3 example IDs; assign a **category tag** (e.g. `EXPRESSION GAP`, `SYSTEM FAILURE`, `EVALUATION BURDEN`, `DEAD END`, `AI EXPECTATION`, `REGRESSION`) | `data/clusters/cluster_labels.json` |
| 4.5 | **Sanity-check clusters** | Sample 5 members per cluster; verify they fit the label; flag mismatches | Console report |
| 4.6 | **Opportunity scoring** | `frequency_share × severity_avg × recency_weight × unresolved_factor`; flag n < 30 as low-confidence | `analysis/opportunity_score.py` → `data/aggregates/opportunity_scores.json` |
| 4.7 | **Generate audit file** | 100 stratified-random items (70 relevant + 30 rejected); `audit.html` with Yes/No toggles; companion `audit.csv` | `analysis/audit_generator.py` → `data/audit/audit.html`, `data/audit/audit.csv` |
| 4.8 | **Run agreement check** | Re-label 300 random items with a different LLM provider; compute agreement on `relevance` and `failure_stage` | `analysis/agreement_check.py` → `data/audit/agreement_report.json` |
| 4.9 | **Compute audit metrics** | Script reads filled-in audit CSV → precision, estimated recall | `data/audit/audit_metrics.json` |
| 4.10 | **Build search index** | Quantise embeddings (≤ 15 MB total); build BM25 index over item text; include filter fields | `index_builder/bm25_index.py` → `data/index/` |
| 4.11 | **Generate narrative observations** | Analyse cluster overlaps, clue × failure intersections, outcome distributions. LLM synthesises 8–12 narrative observations, each with a **pattern → implication** structure. Every number traces to a precomputed aggregate. | `analysis/observations.py` → `data/aggregates/observations.json` |
| 4.12 | **Prepare evidence sets per finding** | For each failure_stage and cluster, select 3–5 representative user quotes (diverse sources, high labeler_confidence). Precompute as expandable evidence bundles. | `data/aggregates/evidence_bundles.json` |

### Opportunity Score — Worked Example

```
Cluster: "Search by description returns wrong results"
  Items:           184   → frequency_share = 184/3400 = 0.054
  Avg severity:    2.4
  Recency weight:  0.88  (weighted avg across items)
  Unresolved:      0.82  (most gave_up or not_found)

  Score = 0.054 × 2.4 × 0.88 × 0.82 = 0.093
  n = 184 → ✅ confident
```

## Phase 5 — Web Application

### Objective
Build a public, fast, mobile-friendly, accessible web application that **tells a story with data**. The app does not just display charts — it leads with insight, supports every claim with real user quotes, and rewards exploration with depth. 6 pages + a tool-bound chat agent.

### Design Principles

| Principle | What It Means in Practice |
|---|---|
| **Insight-first** | Every page leads with what the data *means*, not raw numbers. Headlines and narrative observations come before charts. |
| **Progressive disclosure** | Show the summary at a glance; let users expand into evidence. Never overwhelm on first render. |
| **Every claim is grounded** | Every number, observation, and ranking links back to real user quotes. Evidence is always one click (or one expand) away. |
| **Accessible** | Okabe-Ito colour-blind-safe palette. Never encode meaning by colour alone — pair with icons, labels, and patterns. Font sizes ≥ 14px body. |
| **Mobile-first** | Every layout works at 375px. Cards stack; tables become lists; charts resize. |

### Tasks

| # | Task | Detail | Output |
|---|---|---|---|
| 5.1 | **Initialise Next.js** | `npx create-next-app@latest` with TypeScript, App Router, ESLint | `app/` directory |

### Chat Agent Tool Contract

```typescript
// search_evidence: semantic + keyword search over the corpus
search_evidence(query: string, filters?: Filters, k?: number): EvidenceItem[]

// aggregate: grouped counts from precomputed data
aggregate(group_by: string, filters?: Filters): AggregateResult

// compare: side-by-side comparison of two segments
compare(segment_a: string, segment_b: string, dimension: string): ComparisonResult

// get_review: fetch a single item by ID
get_review(id: string): ReviewItem
```

### Chat Safety Rails

```
1. Max 4 tool calls per user question
2. Numbers ONLY from tool output — never hallucinated
3. "Not enough evidence" if < 3 supporting items
4. Polite refusal for competitor / off-topic questions
5. Embedding failure → fallback to BM25
6. LLM 429 → failover to alternate provider
```

### Evidence Card Spec (Used Across All Pages)

Every evidence card — in chat answers, dashboard findings, and opportunity drill-downs — follows the same design:

```
┌──────────────────────────────────────────────────┐
│ ▎ "I remember the photo had a blue sky but       │
│ ▎  searching 'blue sky' gives me thousands       │
│ ▎  of results"                                   │
│   — Play Store · ★★ · Nov 2025 · 🔗 original   │
└──────────────────────────────────────────────────┘
```

- **Coloured left border** (accent colour, consistent across the app)
- **Exact user quote** in italics
- **Source** badge (Play Store / Reddit / YouTube / App Store / Help Community)
- **Rating** (if applicable)
- **Date**
- **Link** to original post

### Category Tag System

Failure stages and clusters are tagged with coloured badges for scanability:

| Tag | Applies To | Colour |
|---|---|---|
| `EXPRESSION GAP` | `cannot_express` failures | Warm amber |
| `SYSTEM FAILURE` | `system_misunderstands` failures | Coral red |
| `EVALUATION BURDEN` | `results_hard_to_evaluate` failures | Soft blue |
| `DEAD END` | `cannot_refine` failures | Deep grey |
| `INDEX GAP` | `photo_not_indexed_or_missing` failures | Muted teal |
| `AI EXPECTATION` | AI feature mentioned + high severity | Violet |
| `REGRESSION` | `regression_claim = true` | Dark orange |

Colours are from the Okabe-Ito palette; each tag also has an icon so meaning is never encoded by colour alone.

## Risk Register

| Risk | Impact | Mitigation |
|---|---|---|
| YouTube quota exhaustion mid-collection | Delayed Phase 1 | Checkpoint after each query; budget ≤ 9,000/day; resume next day |
| Help Community blocks crawling | Missing ~300 items | Check robots.txt first; if blocked, redistribute target to other sources |
| Core corpus < 3,200 after all sources | Gate at Phase 3 | Extend date window → add Hindi/Hinglish → include adjacent items (labelled) |
| LLM free-tier rate limits | Slow extraction | Batch calls; cache every result; backoff; failover between providers |
| App Store RSS feed deprecated | Missing ~700 items | Fallback to maintained library (e.g. `app-store-scraper`) |
| Vercel cold starts | Slow first request | Precompute everything; keep bundle small; use edge runtime where possible |
| Embedding model too large for Vercel | Deployment failure | Use quantised embeddings (≤ 15 MB); fallback to BM25-only |
